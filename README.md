## الگوریتم پیشنهادی (همان چیزی که در ۳-۲-۴ باید نوشته شود)
- **تابع هدف:** کمینه‌سازی J(σ) = مجموع وزن تراکنش‌هایی که دو حسابشان در دو شارد مختلف‌اند.
- **قید ۱ (BIBD):** σ(a) ∈ Cand(a)؛ هر حساب فقط r شارد مجاز دارد.
- **قید ۲ (ظرفیت):** اندازه هر شارد ≤ ⌈(1+ε)N/S⌉ با ε = 0.05.
- **رویه:**
  1. گروه‌بندی حساب‌ها به v گروه با LDG (گروه‌بندی آگاه از تراکنش)
  2. Cand(a) = {(φ(a) − d) mod v : d ∈ D}
  3. افراز اولیه σ0(a) = π(φ(a)) که π(i) = (i − d0) mod v (تطابق کامل، گزاره شدنی‌بودن)
  4. بهینه‌سازی محلی: هر حساب به شارد کاندیدی منتقل می‌شود که بیشترین کاهش J را بدهد (اگر ظرفیت اجازه دهد)
  5. توقف: پایان بودجه B یا یک دور کامل بدون بهبود
- **بودجه B** = تعداد «ارزیابی کاندید» = 10 × N × r. همه نسخه‌های ablation همین بودجه را دارند.
- **epoch بعدی:** از افراز قبلی شروع می‌کند، پس مهاجرت کم می‌ماند.

## ablation (طبق نظر استاد)
| نسخه | توضیح |
|---|---|
| (1) BIBD no-opt | فقط افراز اولیه σ0 |
| (2) Unconstrained opt | همان بهینه‌سازی، ولی هر حساب می‌تواند به همه S شارد برود |
| (3) Random-constrained opt | r شارد تصادفی برای هر گروه (بدون ساختار BIBD) |
| (4) BIBD-constrained opt | روش پیشنهادی |

شش معیار: `rho_cross`، `CV_L`، `migration`، `time_ms`، `memory_KB`، `objective_J`، به‌علاوه `search_space`.
- مقایسه (2) و (4): هزینه کیفیتی قید BIBD
- مقایسه (3) و (4): آیا ساختار BIBD مهم است یا فقط کوچک بودن فضا

## پروتکل ارزیابی (تقسیم زمانی)
تراکنش‌ها به ترتیب زمان مرتب می‌شوند: ۷۰٪ اول برای ساخت افراز، ۳۰٪ آخر برای سنجش ρ_cross و CV_L.
ساخت افراز دو مرحله دارد (epoch1 = نیمه اول آموزش، epoch2 = کل آموزش) تا مهاجرت قابل اندازه‌گیری باشد.

## گرفتن داده واقعی اتریوم از Google BigQuery
در console.cloud.google.com/bigquery (حساب رایگان کافی است) این کوئری را اجرا و خروجی را CSV ذخیره کن:
```sql
SELECT from_address, to_address, block_number
FROM `bigquery-public-data.crypto_ethereum.transactions`
WHERE block_number BETWEEN 18000000 AND 18000250
  AND to_address IS NOT NULL
```
این بازه (۲۵۱ بلوک) پس از حذف ایجاد قرارداد و خودارجاع، ۳۵٬۵۳۱ تراکنش میان ۲۳٬۶۷۶ حساب می‌دهد (همان داده مقاله). برای داده XBlock-ETH نام ستون‌ها را با `--from-col`، `--to-col` و `--time-col` تنظیم کن.

## نکات مهم برای گزارش در پایان‌نامه
- seed هر اجرا ثبت است؛ نتایج کاملاً تکرارپذیرند.
- زمان و حافظه با `tracemalloc` اندازه‌گیری می‌شوند که خودش کمی سربار دارد؛ برای همه روش‌ها یکسان است.
- بار هر شارد = تعداد تراکنش‌هایی که آن شارد در آن‌ها مشارکت دارد (تراکنش بین‌شاردی برای هر دو شارد حساب می‌شود).
- در بار کاری ساختاریافته، حساب‌های داغ (توزیع توانی) باعث می‌شوند CV_L ذاتاً بالا باشد.
